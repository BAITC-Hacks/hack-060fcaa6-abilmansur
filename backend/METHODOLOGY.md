# Методика v1.0.0

Все выводы — гипотезы для AML-проверки. Нет размеченных ролей, поэтому скоры — прозрачные эвристики, а не оценённые вероятности и не доказательство виновности.

## Подготовка и признаки

Входные таблицы проверяются на наличие полей, null, типы целочисленных идентификаторов, уникальность узлов и пар рёбер, положительные конечные суммы, допустимую глубину и существование концов рёбер. `is_seed` должен соответствовать `depth=0`. Суммы и число транзакций повторно агрегируются из transactions и сверяются с edges (абсолютный допуск суммы 0,011 KZT). Временные признаки считаются по датам, время суток неизвестно. Период определяется по самим данным.

В граф добавляются **все** nodes, включая изолированных seed. Направление src → dst сохраняется. Количество уникальных контрагентов, входящие и исходящие суммы вычисляются без переводов самому себе. Такие переводы, если появятся в новом наборе, остаются в исходном графе и суммарном обороте.

- `in_degree`, `out_degree`: уникальные плательщики и получатели.
- `in_kzt`, `out_kzt`: наблюдаемые потоки за период, не полный баланс.
- `observed_out_in_ratio`: out/in при in > 0, иначе null; показывается как описательная метрика, для seed в правилах не используется.
- `seed_reach`: число различных seed, от которых существует направленный путь до узла. Сам узел не считается своим предком. Это структурная достижимость без проверки последовательности дат, не доказанная трасса средств.
- `betweenness`: нормированная направленная посредническая центральность без весов, приближённо по min(128, N) исходным вершинам, `seed=42`. Большая сумма не интерпретируется как большая длина пути.
- `betweenness_rank`: эмпирический процентиль среди **положительных** значений центральности; нулевым присваивается 0.
- `boundary_censored`: depth=4, исходящие потоки могут быть обрезаны.
- `near_outgoing_day_ratio`: доля дней с входящими, для которых есть исходящие в тот же день или следующие два дня; null, если входящих дней нет.
- `max_same_day_senders`: максимальное число разных плательщиков за день.

Последние два признака показываются в карточке, но не повышают приоритет. Совпадение дат не подтверждает транзит конкретной суммы. `out > in` получает отдельное предупреждение о неполноте баланса.

## Роли: применяется первое подходящее правило

| Очерёдность | Роль | Условие | role_score |
|---|---|---|---|
| 1 | peripheral | in_degree + out_degree = 0 | 0,20 |
| 2 | coordinator | depth < 4; in_degree ≥ 2; out_degree ≥ 2; seed_reach ≥ 3; betweenness > 0; betweenness_rank ≥ 0,90 | 0,65 |
| 3 | consolidator | in_degree ≥ 3 и (depth=4 **либо** не seed и out/in ≤ 0,50) | 0,55 при depth=4; иначе 0,80 |
| 4 | distributor | out_degree ≥ 3 и out_degree ≥ 2 × in_degree | 0,80 |
| 5 | transit | depth < 4; не seed; in_degree ≥ 1; out_degree ≥ 1; 0,80 ≤ out/in ≤ 1,20 | 0,70 |
| 6 | terminal | depth < 4; не seed; in_degree ≥ 1; out_degree=0 | 0,60 |
| 7 | peripheral | ни одно из правил не подошло | 0,30 |

На depth=4 консолидация означает только **сходящиеся наблюдаемые потоки**: наличие денег на счёте неизвестно. Такие узлы никогда не получают terminal. У seed неполны входящие, поэтому правила удержания/транзита к ним не применяются. `terminal` в остальных случаях тоже лишь кандидат по наблюдаемому периоду.

`coordinator` — структурно центральный кандидат для проверки. Он может оказаться обычным сервисным счётом: атрибутов для такого различения нет. `peripheral` означает недостаточность признаков, а не низкий реальный риск. Evidence ограничен 200 символами, полные метрики и предупреждения доступны в API.

## Приоритет

```text
priority = 0,30 × percentile(in_degree)
         + 0,25 × percentile(in_kzt + out_kzt)
         + 0,20 × min(seed_reach / 5, 1)
         + 0,15 × percentile(betweenness)
         + 0,10 × role_weight
```

Процентили вычисляются по положительным значениям, одинаковым значениям присваивается средний ранг; нули остаются нулями. `role_weight`: coordinator=1, consolidator=0,9, transit=0,65, distributor=0,6, terminal=0,45, peripheral=0. Значение в [0,1], округление до 6 знаков. Оно служит порядком просмотра, не порогом автоматической блокировки. Все пять вкладов доступны в карточке и в `why` топ-листа. При равных скорах сортировка по gid по возрастанию.

Изолированный seed получает приоритет 0 в рамках структурной модели: это отсутствие информации для ранжирования, а не снятие исходного подозрения. Статус seed сохраняется, его можно отфильтровать отдельно.

## Кластеры

Взвешенная неориентированная проекция: суммы противоположных направлений **складываются**. Louvain выполняется отдельно внутри каждой слабосвязной компоненты, вес — сумма KZT, разрешение 1, random seed 42. Изоляты получают собственные кластеры. Итоговые группы упорядочены по убыванию размера, затем по минимальному gid; идентификаторы начинаются с 0.

Это позволяет выделить сообщества внутри большой компоненты, а не считать всю её одной группой. `sum_kzt_internal` считает каждое направленное ребро ровно один раз, если оба конца принадлежат кластеру; межкластерный оборот туда не включён. `top_gids` — до пяти узлов по приоритету; в CSV разделены `;`, в JSON — массив строк. Гипотезы описывают структуру, не приписывают преступное назначение.

Одинаковые входные файлы, версия методики и lockfile дают одинаковые результаты. Номера кластеров могут измениться при изменении данных. Не сравнивайте номера кластеров разных запусков как устойчивые идентификаторы групп.

## Ограничения и запросы дополнительных данных

- Граф обрывается на четвёртом колене: нужны исходящие этих узлов и расширение окна наблюдения.
- Входящие за пределами выборки и межбанковские потоки не видны: нужны полные обороты по проверяемым счетам.
- Переводы ниже 5000 KZT исключены: по этому набору нельзя подтвердить или исключить такое дробление.
- Для проверки временного транзита нужны точные timestamps; сопоставление дат само по себе недостаточно.
- Без атрибутов и остатков невозможно отличить легитимный платёжный сервис от подозрительного узла по одной топологии.
- Пороги не обучены. Оценивать подход следует экспертным разбором кандидатов и чувствительностью к порогам/периоду, а не заявлять accuracy.

## Рост до ~1 млн узлов

Текущая реализация хранит таблицы и граф в памяти и предназначена для небольшого батча. NetworkX с Python-объектами и отдельный обход от каждого seed на миллионе узлов потребуют пересмотра.

1. Валидация/агрегация Parquet потоками через DuckDB или Polars, разбиение по периоду.
2. CSR-граф или igraph/NetworKit вместо объектов NetworkX; компоненты и сообщества считать пакетно.
3. Для большого количества seed — распространение битовых множеств/скетчей достижимости, с явной маркировкой приближённых метрик.
4. Betweenness вычислять выборочно внутри интересующих компонент; контролировать ошибку и фиксировать random seed. Для плотных графов отказаться от глобальной центральности в пользу локальных кандидатов.
5. Хранить версионированные результаты в PostgreSQL/Parquet, пересчёт выполнять фоновым заданием с прогрессом и отменой.
6. В UI передавать только кластеры и ограниченные окрестности, серверную пагинацию; полный миллионный граф не отправлять браузеру.
7. AI получает лишь выбранные агрегаты и ссылки; размер графа не должен линейно увеличивать LLM-контекст.
