# Backend — автономный финансовый следователь

Claude (Agent SDK) — главный аналитик: сам пишет SQL и Python, исследует сеть переводов и
восстанавливает структуру группы. Приложение над SDK организует расследование: хранит
состояние между запусками, проверяет каждое утверждение по исходным записям и отдаёт
результат в виде, удобном для графа.

```
FastAPI (app/api)  ──SQLite──  Worker (app/worker.py) ── Claude Agent SDK
   │  SSE прогресс              │  Bash + Python (DuckDB, NetworkX, app.analytics.toolkit)
   │  граф / таймлайн           │  MCP-инструменты доски расследования (app/agent/tools.py)
   └── DuckDB над Parquet ──────┴── проверка ссылок и чисел (app/verification.py)
```

## Датасет-граф и обязательные CSV (`app/pipeline.py`)

Одна команда, без агента и без стадий расследования (на датасете задания 2 248 узлов — около 2 с):

```bash
cd backend
uv run python -m app.pipeline --data ../data --out ./output    # --top 30 — размер top_nodes.csv (минимум 20)
```

На входе папка с тремя файлами: `nodes.parquet` (gid, depth, is_seed), `edges.parquet` (src, dst, sum_kzt,
n_tx, depth), `transactions.parquet` (src, dst, date, sum_kzt). На выходе ровно три файла:

| Файл | Строки | Колонки |
|---|---|---|
| `nodes_roles.csv` | каждый узел (2 248) | `gid, role, role_score, cluster_id, priority_score, rank, evidence` (≤ 200 символов) + признаки: depth, is_seed, censored, seeds_upstream, seeds_direct, retention, peer_in_degree, peer_out_degree, peer_volume, peer_betweenness, depth_outliers, in/out_degree, in/out_tx, in/out_sum_kzt, fast_out_share, sync_in_max, co_senders, routes_mid, routes_any, pagerank, betweenness, hub_in, hub_out, clusters_touched |
| `clusters.csv` | каждый кластер | `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis` + cluster_score, sum_kzt_external, n_edges_internal, n_censored, fast_share_internal, repeated_routes, in/out_kzt_nonseed, in/out_kzt_seeds (приток и отток отдельно для не-seed и seed: у seed вход не виден, поэтому сравнивать приток с оттоком кластера можно только по не-seed), roles |
| `top_nodes.csv` | первые N по приоритету (≥20) | `rank, gid, role, priority_score, why` (схема задания; why ≤ 200 символов) + role_score, cluster_id, seeds_upstream, seeds_direct и ключевые признаки |

Тот же расчёт выполняется при импорте трёх файлов в приложение (`POST /datasets/graph` или
`/datasets/from-path` с папкой), а CSV скачиваются через `GET /datasets/{id}/outputs/{name}`.
Результат детерминирован (фиксированный seed Louvain), все пороги — константы в начале `app/pipeline.py`.

### Ограничения данных, которые учитывают правила

- **Обход только по исходящим**, от 81 seed, 4 колена, переводы ≥ 5 000 ₸ за июль 2026.
- **Цензура 4-го колена.** 444 узла глубины 4 не раскрывались: их `out_degree = 0` значит «неизвестно».
  Такие узлы помечены `censored = true` и **никогда не получают роль `terminal`**; распределителем или
  транзитом они тоже быть не могут (исходящие не наблюдались).
- **Входящие неполны.** Входящий перевод виден, только если отправитель сам был обойдён; у seed входящих
  почти нет. Поэтому **баланс не используется как самостоятельный признак ни в одном правиле роли**.
  Доля удержанного (`retention = 1 − out/in`) считается только для узлов **не seed, не censored и с видимым
  входом** (у остальных пусто) и лишь уточняет балл транзита. Если узел отдаёт больше, чем видно на входе,
  `evidence` прямо говорит «отдаёт в N раз больше видимого входа» — часть входа вне данных.
- **Дата без времени.** «Пришло → ушло» = исходящий перевод в тот же день или до 2 дней после входящего;
  порядок внутри дня неизвестен, поэтому совпадение в один день — возможная, а не доказанная передача.

### Признаки узла

| Признак | Как считается |
|---|---|
| `in_degree`, `out_degree` | число уникальных отправителей / получателей (по `edges`) |
| `in_sum_kzt`, `out_sum_kzt`, `in_tx`, `out_tx` | суммы и число переводов по рёбрам |
| `censored` | `depth == max(depth)` (4): исходящие не наблюдались |
| `fast_out_share` | доля суммы исходящих, отправленных в день d, если в [d − 2, d] было хотя бы одно поступление; 0, если входящих не видно |
| `sync_in_max` | максимум различных отправителей узлу в один день (синхронные поступления) |
| `co_senders` | сколько других отправителей платили тем же получателям в те же дни |
| `routes_mid`, `routes_any` | повторяющиеся маршруты A → B → C (B переводит C за 0–2 дня после поступления от A) на ≥ 2 разных днях: узел как B / в любой позиции |
| `pagerank` | PageRank направленного графа, вес = sum_kzt |
| `betweenness` | посредническая центральность (точно до 20 000 узлов, дальше выборка k = 2000) |
| `hub_in`, `hub_out` | сколько узлов-хабов (консолидатор / распределитель / транзит) среди отправителей / получателей |
| `clusters_touched` | число других кластеров среди соседей |
| `seeds_upstream` | сколько **разных seed** имеют направленный путь к узлу длиной ≤ **3** перевода (seed не считает сам себя) |
| `seeds_direct` | сколько разных seed платят узлу напрямую |
| `retention` | 1 − out_sum / in_sum, только для не-seed, не-censored узлов с входом > 0; иначе пусто |

**Сравнение с узлами своего колена (детекция аномалий).** Структура сети сильно зависит от глубины: у узла
4-го колена максимум 3 плательщика, у seed — до 24. Поэтому для in_degree, out_degree, оборота (in + out) и
betweenness считается `peer_<метрика>` — доля узлов **того же колена** со строго меньшим значением (0–1; общее
для большинства значение даёт 0, а не «высокий перцентиль»). Seed сравниваются только с seed (вход у них
одинаково неполон), out_degree на 4-м колене не сравнивается (цензура). `depth_outliers` — метрики, где узел
выше **95%** своего колена: на датасете задания это 239 узлов на всех коленах. В `evidence` это звучит как
«по числу плательщиков выше 98% узлов 3-го колена».

**Главная идея приоритета.** 81 seed — уже известный нижний уровень («курьеры»). Задача — подняться выше:
узел, в который сходятся деньги от нескольких разных seed (напрямую или через 1–2 промежуточных узла), —
главный кандидат в точку консолидации. Поэтому `seeds_upstream` входит и в правило `consolidator`, и в приоритет.

`pct(x)` — перцентиль среди узлов с x > 0 (нулевые значения остаются 0). `cap(x, a) = min(1, x / a)`.

### Роли (словарь задания) и пороги

Правила проверяются по порядку; узел получает первую подходящую роль. Внутренние роли доски агента
сопоставляются так: collector → consolidator, final_recipient → terminal, organizer / coordinated_account →
coordinator, source / unclear → peripheral.

| Роль | Правило (все условия) | role_score |
|---|---|---|
| `consolidator` | (in_degree ≥ **5** и in_degree ≥ **2** × out_degree) **или** (seeds_upstream ≥ **3**, in_degree ≥ **2** и in_degree ≥ out_degree — деньги нескольких seed сходятся в узле) | 0.3·cap(in_degree, 15) + 0.3·cap(seeds_upstream, 8) + 0.15·cap(sync_in_max, 5) + 0.25·pct(in_sum) |
| `distributor` | не censored; out_degree ≥ **5** и out_degree ≥ **2** × max(in_degree, 1) | 0.5·cap(out_degree, 30) + 0.25·fast_out_share + 0.25·pct(out_sum) |
| (если выполнены оба правила — роль с бо́льшим role_score) | | |
| `transit` | не censored, не хаб; есть входящие и исходящие; fast_out_share ≥ **0.5** и ≥ **2** быстрых исходящих перевода | 0.45·fast_out_share + 0.2·(1 − retention, пусто → 0.5) + 0.15·cap(routes_mid, 3) + 0.2·pct(betweenness) |
| `coordinator` | не хаб и не транзит; (hub_in + hub_out ≥ **3**, hub_in ≥ 1 и hub_out ≥ 1) **или** (pct(betweenness) ≥ **0.98** и clusters_touched ≥ **2**) | 0.4·cap(hub_in + hub_out, 4) + 0.3·pct(betweenness) + 0.3·cap(clusters_touched, 3) |
| `terminal` | **не censored**, out_degree = 0, in_degree ≥ 1 | 0.4 + 0.2·cap(in_degree, 5) + 0.2·cap(seeds_upstream, 8) + 0.2·pct(in_sum) |
| `peripheral` | всё остальное (включая censored-узлы без других признаков) | 1 − max(силы четырёх активных ролей) — насколько узел однозначно периферийный |

На датасете задания: terminal 1034, peripheral 843, consolidator 121, distributor 120, transit 89, coordinator 41.

### Кластеры

Louvain (`networkx`, resolution 1.0, seed 7) на неориентированном графе, вес ребра = log(1 + sum_kzt), чтобы
несколько крупных переводов не определяли разбиение. Louvain не объединяет несвязные компоненты, изолированные
узлы — отдельные кластеры. Номера кластеров отсортированы по подозрительности (0 — самый подозрительный):

`cluster_score = 0.35·cap(доля активных ролей, 1/3) + 0.25·fast_share_internal + 0.20·cap(repeated_routes, 3)
+ 0.20·pct(sum_kzt_internal)`; для кластеров меньше 3 узлов — 0. `hypothesis` строится по составу ролей
(сбор → транзит → распределение, веерная раздача, цепочки транзита…) с фактами, ключевым узлом, числом
цензурированных узлов и обычным объяснением (зарплата, продавец, выплаты поставщикам).

### Priority score (0–1) и rank

```
raw = 0.25 · ROLE_WEIGHT[role] · role_score
    + 0.25 · (0.6·cap(seeds_upstream, 8) + 0.4·cap(seeds_direct, 3))          # сходимость денег seed
    + 0.20 · (0.4·fast_out_share + 0.2·cap(sync_in_max, 5) + 0.3·cap(routes_any, 3) + 0.1·cap(co_senders, 5))
    + 0.15 · (0.5·pct(pagerank) + 0.5·pct(betweenness))
    + 0.10 · pct(in_sum + out_sum)
    + 0.05 · cluster_score(cluster)
priority = raw × (0.6 для seed, иначе 1)
ROLE_WEIGHT: consolidator / coordinator 1.0, distributor / transit 0.9, terminal 0.5, peripheral 0.1
```

`rank` — место по убыванию priority (1 = самый приоритетный, без совпадений). Приоритет seed умножается
на 0.6: они уже известны следствию, и рейтинг должен вести к неизвестным уровням выше них (на датасете
задания в топ-20 seed нет, но очень центральный seed всё равно может подняться).

`evidence` / `why` (≤ 200 символов) — формулировка-гипотеза («Признаки консолидации: …») и факты по
важности: от скольких seed приходят деньги, от скольких плательщиков и скольким получателям, какую долю
отдаёт дальше, насколько быстро, синхронность, повторяющиеся маршруты, граница обхода, пометка seed.
Факты, не влезающие в 200 символов, отбрасываются с конца. Пример:
«Признаки консолидации: деньги от 9 seed (2 напрямую); получает от 8 плательщ. (2.2 млн ₸); платит 2 получат.
(517 тыс ₸); отдаёт дальше 24% полученного; 99% уходит ≤2 дн. после поступления».

### Устойчивость сети (бонус, не входит в CSV)

`pipeline.resilience` / `GET /datasets/{id}/resilience`, вкладка «Устойчивость» на экране сети: из графа изымаются
топ-N узлов по приоритету (seed не изымаются) и для сравнения N случайных не-seed узлов (среднее по 20 попыткам).
Считаются крупнейший фрагмент, число фрагментов и сколько узлов ещё достижимо от seed (≤ 4 переводов). На датасете
задания: без топ-20 деньги от seed доходят до 1 742 узлов вместо 2 167 (−20%), сеть распадается с 16 до 91
фрагмента; без 20 случайных — −1,5%. Без топ-50 — −35% против −5%.

### Что изменится при масштабе ~1 млн узлов

- **Betweenness** — O(V·E), точно не считается: уже включается выборка k = 2000 опорных узлов после
  20 000 узлов; для 1 млн — приближение по выборке или замена на k-hop / bridge-признаки.
- **Кластеризация** — networkx Louvain однопоточный и медленный: заменить на Leiden (igraph / leidenalg) или
  GPU (cuGraph), считать по связным компонентам параллельно.
- **Временные признаки** — коррелированный `EXISTS` и self-join по (получатель, день) растут квадратично у
  популярных получателей: перейти на ASOF JOIN / оконные функции DuckDB, ограничить число пар на группу.
  Повторяющиеся маршруты — только по кандидатам с высоким приоритетом или партиционировать по дням.
- **Нормализация** — перцентили относительны к сети; на миллионе узлов лучше зафиксировать калиброванные
  пороги (или считать перцентили внутри сегментов: физлица / юрлица, регион), иначе баллы плывут между выгрузками.
- **Память и вывод** — признаки держать в Parquet / DuckDB вместо pandas; `evidence` генерировать только для
  top-K; `nodes_roles.csv` в 1 млн строк лучше отдавать в Parquet.
- **Данные** — при большей глубине обхода цензурированная граница растёт; без обхода входящих неполнота
  входящих остаётся, поэтому правила по-прежнему не должны опираться на баланс.
- **Агент** — не читает выгрузку целиком, а работает через SQL-представления `node_roles` / `clusters`
  и проверяет верх рейтинга.

### Проверки агента на графе

Числа агент берёт у приложения, а не считает сам. Приложение проверяет конкретные факты; гипотезы о ролях
остаются гипотезами, эталонной разметки нет.

- `node_card(gid)` — карточка узла из расчёта пайплайна: глубина, seed, наблюдались ли исходящие, суммы,
  число переводов и контрагентов, доля переданного дальше, seed выше по потоку, главные отправители и
  получатели, готовые фразы с числами. Агент цитирует их, а не пересчитывает проценты.
- `set_member` не даёт роль `final_recipient` узлу, который в данных переводит деньги дальше, или узлу на
  4-м колене (исходящие не наблюдались).
- `finish_run` перечисляет узлы из топ-20 рейтинга, которые запуск ни разу не разобрал (как кандидата, покрытие,
  участника, доказательство или ответ); завершить можно, только явно написав, какие не проверены.

## Как устроено расследование

**Этапы** (методы выбирает Claude, `set_stage` проверяет предпосылки, но только предупреждает — переход не
блокируется; обязательные CSV считает пайплайн выше, этапы — дополнительный разбор):

| Этап | Что сохраняется | Условие перехода |
|---|---|---|
| `data_study` | паспорт датасета и ограничения | — |
| `network_overview` | покрытие сети, очередь кандидатов | паспорт сохранён |
| `candidate_review` | статусы кандидатов с причинами | ≥2 сетевых обзора разными методами, ≥2 кандидата |
| `structure_recovery` | версии: участники, связи, маршруты, доказательства | — |
| `refutation` | возражения, альтернативы, ослабленные связи | есть хотя бы одна версия |
| `done` | итог | у каждой версии рассмотрены возражения, открытых нет |

**Постоянное состояние** (`app/db.py`) не зависит от истории чата: паспорт, покрытие
(«какие части сети уже исследованы»), очередь кандидатов, версии, доказательства. Каждый
новый запуск получает сводку доски (`app/agent/state.py`) и продолжает с текущего этапа.

**Доска версий:** версия → участники (наблюдаемая роль, основание включения, альтернативное
объяснение, чего не хватает), связи, маршруты, возражения, открытые вопросы. Ревизия создаётся
новой версией с `parent_id`, а старая сохраняется.

**Роли на доске только наблюдаемые:** `source`, `collector`, `distributor`, `transit`,
`final_recipient` («конечный получатель в доступных данных»), `coordinated_account`, `unclear`
(в выгрузке — словарь задания, см. выше).
Для `organizer` нужно ≥3 доказательств. Обналичивание не утверждается.

## Защита от неточностей (`app/verification.py`)

Перед публикацией приложение пересчитывает всё по исходному Parquet:

- **Доказательство:** все `tx_ids` существуют; заявленные количество и суммы совпадают
  (допуск 0.5%, суммы только в пределах одной валюты); транзакции входят в объявленный период;
  указан SQL-запрос (`query_id`) или скрипт (сохраняется снимок содержимого и sha256).
  Если проверка не прошла, доказательство не сохраняется, и агент должен исправить ошибку.
- **Связь:** направление каждого перевода; статистику считает приложение, а не агент.
- **Маршрут A→B→C:** непрерывность, порядок во времени и **неоднозначность атрибуции**
  на каждом узле: доля входящих от маршрута среди всех поступлений в окне, число других
  отправителей. Маршрут публикуется как `possible_route_ambiguous` или `consistent_sequence`
  и никогда не выдаётся за доказанный путь тех же денег.
- **Данные без потерь:** при загрузке сохраняются все исходные колонки (`raw_*`) и отдельные
  переводы. Агрегированные рёбра — только дополнительное представление.
- **Исходные данные:** SQL-инструмент выполняет только SELECT, а DuckDB видит только папку датасета.
  Parquet после загрузки получает права только на чтение (444).

## Запуск локально

```bash
cd backend
uv sync
cp .env.example .env              # ключ не нужен — см. «Авторизация»
uv run python scripts/generate_synthetic.py --out data/synthetic   # тестовые данные + ground truth

uv run uvicorn app.api.main:app --reload --port 8000   # терминал 1
uv run python -m app.worker                            # терминал 2

curl -X POST localhost:8000/datasets/from-path -H 'content-type: application/json' \
  -d '{"path": "../data"}'        # папка с nodes/edges/transactions.parquet; имя по умолчанию = имя папки
curl -X POST localhost:8000/investigations -H 'content-type: application/json' \
  -d '{"dataset_id": "<ds_id>", "title": "Поиск группы"}'
curl -N localhost:8000/investigations/<inv_id>/events          # прогресс (SSE)

uv run python scripts/evaluate.py <inv_id> data/synthetic/ground_truth.json   # точность/полнота
uv run pytest
```

## Авторизация и версия CLI

Agent SDK не обращается к API сам: он запускает CLI Claude Code. `CLAUDE_CLI_PATH`
(по умолчанию `~/.local/bin/claude`) указывает на ваш установленный `claude`, поэтому агент
всегда работает на той же версии, что и у вас. Если путь пустой, SDK берёт свою встроенную копию
CLI, и её версия может отставать.

CLI берёт вход так: если задан `ANTHROPIC_API_KEY`, оплата идёт по ключу за токены; если нет,
используется сохранённый вход Claude Code, то есть ваша подписка. По подписке запуски расходуют
её лимиты. `AGENT_MAX_BUDGET_USD` ограничивает *оценочную* стоимость запуска, а не реальный
счёт. Если лимит подписки закончится посреди запуска, доска расследования останется
сохранённой, и новый запуск продолжит с того же места.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/datasets` (multipart) · `/datasets/from-path` | загрузка CSV/Parquet, нормализация, профиль (путь к папке → граф) |
| POST | `/datasets/graph` (multipart: nodes, edges, transactions, name) | импорт графа из трёх Parquet + расчёт CSV |
| GET | `/datasets/{id}/outputs[/{name}]` · POST `/datasets/{id}/pipeline` | CSV-результаты · пересчёт |
| POST | `/investigations` | создать расследование (сразу ставит запуск в очередь, если `start=true`) |
| GET | `/investigations/{id}` · `/board` | состояние и доска: кандидаты, покрытие, версии целиком |
| POST | `/investigations/{id}/runs` | новый запуск `investigate` / `message` / `question` / `challenge` (продолжает сессию агента) |
| POST | `/investigations/{id}/ask` | вопрос по узлу: `mode` = `why` / `connections` / `challenge` / `free` |
| GET | `/runs/{id}/events` · `/investigations/{id}/events` | SSE-прогресс (поддерживает `Last-Event-ID`) |
| POST | `/runs/{id}/cancel` | остановка запуска |
| GET | `/investigations/{id}/versions/{vid}/graph?context=N` | граф в формате Graphology `import()` |
| GET | `/investigations/{id}/versions/{vid}/timeline?bucket=day` | кадры для воспроизведения по времени |
| GET | `/investigations/{id}/evidence[/{eid}]` · `POST …/reverify` | пакет доказательств с транзакциями |
| GET | `/investigations/{id}/accounts/{acc}` | карточка счёта: участие в версиях, доказательства, ответы |
| POST | `/investigations/{id}/transactions` | открыть конкретные транзакции по ID |
| GET | `/investigations/{id}/workspace[/file]` | код и заметки, написанные агентом |

Статусы запуска: `queued` → `running` → `completed` / `stopped` (достигнут лимит ходов или
бюджета; доска сохранена, следующий запуск продолжит) / `failed` / `cancelled`.

## Настройки

`CLAUDE_CLI_PATH`, `AGENT_MODEL` (по умолчанию `claude-opus-5`), `AGENT_EFFORT`, `AGENT_MAX_TURNS`,
`AGENT_MAX_BUDGET_USD`, `REPORT_LANGUAGE` (`ru`), `WORKER_CONCURRENCY`, `SQL_MAX_ROWS` — см. `.env.example`.
